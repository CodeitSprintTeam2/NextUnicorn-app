## 마일스톤 1 — 2026-10-15 시연 흐름

### ISSUE-01 프로젝트 실행 및 첫 배포 기반 만들기

- 우선순위: `P0`
- 선행 이슈: 없음
- 목표: React와 Express가 연결된 최소 서비스를 Netlify와 Render에 배포한다.

작업:

- React(JavaScript), React Router, axios 클라이언트 구성
- Express 5 서버 구성
- Prisma 7과 PostgreSQL 연결 구성
- `GET /api/health` 상태 확인 API 구현
- `CLIENT_ORIGIN`에 지정된 Origin만 허용하는 Express `cors` 설정
- 클라이언트에서 환경 변수로 API 주소 사용
- Netlify와 Render 배포 및 클라이언트 라우팅 설정

완료 기준:

- 로컬에서 클라이언트와 서버를 각각 실행할 수 있다.
- `GET /api/health`가 계약된 `200 OK` 응답을 반환한다.
- Netlify 배포 주소에서 화면이 열리고 Render 서버 요청이 성공한다.
- 로컬에서는 Vite 주소, 배포에서는 Netlify 주소의 요청만 CORS를 통과한다.
- 허용되지 않은 Origin을 `Access-Control-Allow-Origin`으로 응답하지 않는다.
- 배포 환경에 DB 연결 문자열과 API 주소가 저장소에 노출되지 않는다.
- 허용된 기술 외 라이브러리를 추가하지 않는다.

### ISSUE-02 기업 초기 데이터와 카테고리 준비하기

- 우선순위: `P0`
- 선행 이슈: ISSUE-01
- 목표: 기업 목록과 상세 화면에서 사용할 기업·카테고리 데이터를 DB에 준비한다.

작업:

- `Category`, `Company` 마이그레이션 적용
- 카테고리와 기업 시드 데이터 작성
- 기업 필수 값과 실제 누적 투자 금액·매출·고용 인원 범위 검증
- 시드 입력 데이터에서 같은 기업명이 두 번 이상 사용되지 않았는지 검증
- 카테고리는 이름 기준, 기업은 `Company.name` 기준 `upsert` 적용

완료 기준:

- 빈 DB에 마이그레이션과 시드를 순서대로 적용할 수 있다.
- 각 개발자가 자신의 로컬 DB에 같은 마이그레이션과 기준 시드를 적용할 수 있다.
- 모든 기업이 정확히 하나의 카테고리를 가진다.
- 기업명, 소개, 카테고리, 실제 누적 투자 금액, 매출액, 고용 인원이 누락되지 않는다.
- `Company.actualInvestment`에 시드의 실제 누적 투자 금액이 저장된다.
- 실제 누적 투자 금액과 매출은 PostgreSQL `BIGINT` 범위의 음수가 아닌 값이다.
- 시드를 두 번 실행해도 기업과 카테고리가 중복되지 않는다.
- 시드 입력 데이터에 같은 기업명이 있으면 시드를 적용하지 않는다.
- 같은 이름의 기업이나 카테고리가 이미 있으면 새 행을 만들지 않고 해당 행을 갱신한다.

### ISSUE-04 기업 상세와 투자 목록 조회하기

- 우선순위: `P0`
- 선행 이슈: ISSUE-03
- 목표: 기업 상세 정보와 해당 기업의 투자 내역을 조회한다.

작업:

- `Investment` 마이그레이션 적용
- `GET /api/companies/:companyId` 구현
- `GET /api/companies/:companyId/investments` 구현
- 투자 목록 API에 기본값 `page=1`, `limit=10`과 페이지네이션 메타데이터 적용
- `/companies/:companyId` 상세 화면 구현
- 상세 정보와 투자 목록의 로딩·빈 목록·실패 상태 분리

완료 기준:

- 상세 화면에서 기업 정보, `actualInvestment`, 계산된 `virtualInvestment`를 확인할 수 있다.
- 투자 목록은 `API.md`에 정의된 최신 등록순과 동시간 `id` 내림차순으로 표시된다.
- 첫 화면은 투자 목록의 첫 페이지를 기본 제한 개수만큼 표시한다.

- soft delete된 투자는 목록과 `virtualInvestment`에서 제외된다.
- 잘못된 `companyId`는 `400 INVALID_PATH_PARAMETER`를 반환한다.
- 잘못된 페이지 값은 `400 INVALID_QUERY`를 반환한다.
- 존재하지 않는 기업은 계약된 `404 COMPANY_NOT_FOUND`를 반환한다.
- 상세 정보 요청 실패와 투자 목록 요청 실패를 화면에서 구분할 수 있다.

### ISSUE-05 기업 상세에서 가상 투자 등록하기

- 우선순위: `P0`
- 선행 이슈: ISSUE-04
- 목표: 사용자가 기업 상세에서 투자를 등록하고 목록에서 결과를 확인한다.

작업:

- 투자 등록 모달 구현
- `POST /api/investments` 구현
- 입력값과 비밀번호 확인 검증
- bcrypt 비밀번호 해시 저장
- 등록 성공 후 모달 닫기, 투자 목록과 가상 투자 합계 갱신

완료 기준:

- `API.md` 입력 검증 규칙에 따라 투자자 이름과 코멘트의 앞뒤 공백을 제거한 뒤 길이를 검증하고, 비밀번호 길이를 검증한다.
- `amount`는 `API.md`에 정의된 형식과 범위만 허용한다.
- 비밀번호와 비밀번호 확인이 다르면 `400 VALIDATION_ERROR`를 반환한다.
- 존재하지 않는 투자 대상 기업은 `404 COMPANY_NOT_FOUND`를 반환한다.
- DB에는 비밀번호 원문이 없고 bcrypt 해시만 저장된다.
- 등록 성공 응답에 비밀번호와 해시가 포함되지 않는다.
- 등록 성공 응답의 `amount`는 원 단위의 10진수 문자열이다.
- 등록한 투자가 상세 목록에 나타나고 `virtualInvestment`가 투자 금액만큼 증가한다.
- 목록 → 상세 → 등록 → 등록 결과 확인 흐름이 배포 환경에서 이어진다.

### ISSUE-06 2026-10-15 시연 흐름 배포 검증하기

- 선행 이슈: ISSUE-01~05

작업:

- Render 환경 변수의 `DATABASE_URL`이 로컬 DB와 분리되어 있는지 확인
- Netlify 새로고침 라우팅 확인
- 핵심 흐름 수동 검증
- 발견한 P0 결함 수정 후 재검증

완료 기준:

- 새 DB 기준으로 배포 절차를 재현할 수 있다.
- Render DB에는 저장소의 기존 마이그레이션만 적용하고 배포 과정에서 새 마이그레이션을 생성하지 않는다.
- Render DB에는 카테고리와 기업 기준 데이터만 시드하고 개발용 가상 투자·비교 이력을 넣지 않는다.

- 등록한 투자가 DB와 상세 목록에 한 번만 생성된다.
- 브라우저 콘솔에 처리되지 않은 오류가 없다.
- 팀원 한 명이 아닌 다른 팀원이 배포 주소에서 핵심 흐름을 끝까지 재현한다.

## 마일스톤 2 — 2026-10-21 기능 완성

### ISSUE-07 기업 목록 검색·정렬·페이지 이동하기

- 우선순위: `P1`
- 선행 이슈: ISSUE-03
- 목표: 기업이 많아도 원하는 기업을 탐색한다.

작업:

- 기업명 부분 일치 검색 구현
- 실제 누적 투자 금액·매출액·고용 인원 정렬 구현
- 서버 페이지네이션과 화면 페이지 이동 구현
- 검색 또는 정렬 변경 시 첫 페이지로 이동

완료 기준:

- `page`, `limit`, `search`, `sortBy`, `order`가 `API.md` 계약대로 동작한다.
- 검색은 기업명 부분 일치 결과만 반환한다.
- `sortBy`를 생략하면 `id` 오름차순으로 정렬한다.
- 정렬 값이 같으면 `company.id` 오름차순을 최종 기준으로 사용한다.
- `sortBy` 없이 `order`만 전달하면 `400 INVALID_QUERY`를 반환한다.
- 허용되지 않은 쿼리는 `400 INVALID_QUERY`를 반환한다.
- 검색·정렬·페이지 변경 후 화면과 URL 요청 값이 일치한다.
- 마지막 페이지와 결과가 없는 경우에도 잘못된 페이지 버튼을 표시하지 않는다.

### ISSUE-09 기업 선택 완료와 비교 결과 확인하기

- 우선순위: `P1`
- 선행 이슈: ISSUE-03, ISSUE-02
- 목표: 내 기업과 비교 기업을 선택하고 한 화면에서 비교 결과를 확인한다.

작업:

이 이슈는 하나의 상위 이슈로 관리하고 아래 세 하위 작업의 담당과 진행 상태를 체크리스트로 나눈다.

선택과 비교 결과:

- `Comparison`, `ComparisonTarget` 마이그레이션 적용
- `/compare` 선택 단계와 결과 단계 구현
- 내 기업 1개, 비교 기업 1~5개 선택 구현
- 기업 검색·페이지 이동 구현
- `POST /api/comparisons` 트랜잭션 구현

선택 이력:

- 선택 완료 시 `Comparison`과 `ComparisonTarget` 이력 저장
- 선택 완료 중복 클릭 방지

비교 현황:

- `GET /api/comparison-status` 구현
- `/compare/status` 화면 구현
- `Comparison`과 `ComparisonTarget` 이력에서 선택 횟수 집계

완료 기준:

- 비교 기업이 1~5개일 때만 선택을 완료할 수 있다.
- 내 기업 중복, 비교 기업 중복, 존재하지 않는 기업을 서버가 거부한다.
- 비교 기업 수나 중복이 올바르지 않으면 `400 VALIDATION_ERROR`를 반환한다.
- 요청한 기업 중 하나라도 존재하지 않으면 `404 COMPANY_NOT_FOUND`를 반환한다.
- 선택 완료 한 번에 `Comparison` 한 행과 대상 수만큼 `ComparisonTarget`이 함께 생성된다.
- 일부 저장에 실패하면 비교 이력이 전혀 남지 않는다.
- 선택 완료 요청이 처리 중인 동안 완료 버튼을 다시 누를 수 없으며, 같은 사용자 동작으로 비교 이력과 선택 횟수가 중복 생성되지 않는다.
- 내 기업 선택 횟수는 `Comparison`, 비교 기업 선택 횟수는 `ComparisonTarget`에서 집계한다.
- 선택된 적이 없는 기업도 두 선택 횟수를 `0`으로 표시한다.
- 선택 횟수 현황은 페이지네이션과 두 횟수 기준 정렬을 지원한다.
- `sortBy`를 생략하면 선택 횟수 현황을 `company.id` 오름차순으로 정렬한다.
- 선택 횟수가 같으면 `company.id` 오름차순을 최종 기준으로 사용한다.
- 응답에는 내 기업과 비교 기업 정보 및 `actualInvestment`가 포함된다.
- 새로고침하면 선택 상태가 초기화된다.

완료 기준:

- 응답의 내 기업 순위가 전체 기업 정렬 결과와 일치한다.
- 순위는 `order`와 관계없이 기준값이 큰 기업부터 계산한다.
- 기준값이 같은 기업은 공동 순위로 처리하고 다음 순위는 동점 기업 수만큼 건너뛴다.
- 동점 기업은 `company.id` 오름차순으로 표시하되 이 기준으로 공동 순위를 나누지 않는다.
- 기업이 5개 이상이면 가능할 때 내 기업을 포함해 근접한 5개를 반환한다.
- 상위 또는 하위 경계에서도 가능한 반대 방향 기업을 포함해 최대 5개를 반환한다.
- 허용되지 않은 순위 기준은 `400 INVALID_QUERY`를 반환한다.
- 기업 비교와 순위가 모두 `/compare` 주소 안에서 단계로 전환된다.

### ISSUE-12 가상 투자 수정하기

- 선행 이슈: ISSUE-05

### ISSUE-13 가상 투자 soft delete하기

- 우선순위: `P1`
- 선행 이슈: ISSUE-05
- 목표: 올바른 비밀번호를 입력한 사용자가 투자 내역을 soft delete한다.

작업:

- 투자 삭제 확인 모달 구현
- `DELETE /api/investments/:investmentId` 구현
- bcrypt 비밀번호 비교 후 `deletedAt` 기록
- 삭제 성공 후 목록과 가상 투자 합계 갱신

완료 기준:

- 삭제 성공 시 행은 남고 `deletedAt`에 삭제 시각이 기록된다.
- 비밀번호가 누락되었거나 형식이 올바르지 않으면 `400 VALIDATION_ERROR`를 반환한다.
- 성공 응답은 본문 없는 `204 No Content`다.
- 비밀번호 불일치는 `401 INVALID_PASSWORD`를 반환하며 `deletedAt`이 바뀌지 않는다.
- 이미 삭제된 투자는 다시 삭제하거나 수정할 수 없다.
- 삭제한 투자는 목록에서 사라지고 `virtualInvestment`에서 해당 금액이 빠진다.

### ISSUE-14 전체 기업 투자 현황 조회하기

- 우선순위: `P1`
- 선행 이슈: ISSUE-05
- 목표: 기업별 가상 투자 합계, 실제 누적 투자 금액과 순위를 조회한다.

작업:

- `GET /api/investment-status` 구현
- `/investments` 화면 구현
- 활성 투자 합계와 선택한 투자 금액 기준의 순위 계산
- 서버 페이지네이션과 가상 투자 합계·실제 누적 투자 금액 정렬 구현
- 로딩·빈 목록·실패 상태 표시

완료 기준:

- 모든 기업에 대해 기업 정보, `virtualInvestment`, `actualInvestment`, 순위를 반환한다.
- `virtualInvestment`와 `actualInvestment`는 원 단위의 10진수 문자열이다.
- 가상 투자 내역이 없는 기업도 `virtualInvestment: "0"`으로 포함한다.
- soft delete된 투자 금액은 `virtualInvestment`와 그 기준 순위에 반영되지 않는다.
- `sortBy`를 생략하면 `virtualInvestment` 내림차순으로 정렬한다.
- `sortBy` 없이 `order`만 전달하면 `400 INVALID_QUERY`를 반환한다.
- 투자 금액이 같은 기업은 공동 순위로 처리하고 `company.id` 오름차순으로 표시한다.
- 순위는 항상 투자 금액이 큰 기업부터 계산하며 `order`는 표시 순서만 바꾼다.
- `page`, `limit`, `sortBy=virtualInvestment|actualInvestment`, `order`가 계약대로 동작한다.
- 페이지를 이동해도 순위가 전체 결과 기준으로 유지된다.
- 허용되지 않은 쿼리는 `400 INVALID_QUERY`를 반환한다.
- 응답 모양이 `API.md`와 일치한다.
